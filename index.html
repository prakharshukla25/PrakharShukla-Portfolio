02 / PERSONAL PROJECT · THIS PORTFOLIO

A small website.
A real delivery workflow.

I built this portfolio as a practical DevOps project: version-controlled source, automated checks, a container smoke test, and repeatable publishing. The workflow is in the repository, so the implementation can be inspected.

Inspect the source ↗
THE PROBLEM I WANTED TO SOLVE

Publishing should be a process I can repeat.

A portfolio still needs a dependable path from an edit to a published page. I wanted changes checked before release, a way to test the packaged site, and blog previews that could refresh without rewriting HTML every time.

WHAT I BUILT

A static HTML, CSS, and JavaScript site with a GitHub Actions pipeline. PowerShell handles validation, packaging, and RSS rendering. Bash runs the Docker smoke checks. GitHub Pages hosts the verified artifact.

Azure, Terraform, and AKS are part of my professional toolkit. This particular site is hosted on GitHub Pages.

THE ACTUAL DELIVERY PATHWorkflow YAML ↗
  1. 01
    Change & review

    A pull request runs checks. A push to main follows the deployment path.

  2. 02
    Validate & package

    Check HTML, links, assets, JavaScript syntax, and RSS tests; build an isolated _site artifact.

  3. 03
    Test the container

    Start unprivileged NGINX in Docker, wait for /healthz, and check the homepage and résumé.

  4. 04
    Publish the artifact

    Deploy to GitHub Pages with OIDC after the checks pass.

Content follows the same path. The Wix RSS feed supplies two recent posts; a configured featured article stays pinned. A scheduled run refreshes the published page approximately every six hours.

WHY EACH TOOL IS HERE

Every part has a job.

GitHub Actions
Orchestrates pull request checks, the build, container tests, and deployment. The workflow also supports manual and scheduled refreshes.
PowerShell
Validates the page and assets, packages the static output, safely renders RSS posts, and writes deployment metadata and SHA-256 checksums.
Bash & curl
Run the container smoke test and bounded readiness retries. A started container must respond successfully before the pipeline proceeds.
Docker & NGINX
Provide a reproducible preview and CI test environment, running as a non-root user with a read-only filesystem and dropped capabilities.
GitHub Pages
Serves the verified static files. OIDC handles deployment authentication without a personal access token in the workflow.
REPEATABLE PUBLISHING

A push starts the release.

Once checks pass on main, the workflow publishes the built artifact through GitHub Pages.

CONTENT AUTOMATION

New posts, less upkeep.

Blog previews refresh at build time, with a fixed featured slot and no bot commits added to the repository.

A CLEAR FAILURE BOUNDARY

A failed check stops the release.

Build, feed, or smoke-test failures prevent the new artifact from being published. The existing live version stays available.

DECISIONS & LESSONS

The details behind the diagram.

Why use Docker when the site runs on GitHub Pages?

Docker packages NGINX and the generated site into a repeatable preview and smoke-test environment. GitHub Pages serves the final static artifact. Keeping those responsibilities clear makes the setup easier to explain and maintain.

What did a failed container check teach me?

A container can start before NGINX is ready to answer requests. A connection-reset failure in the smoke test led to bounded retries against the health endpoint, with timeouts and container logs retained for diagnosis.

How does the blog refresh stay predictable?

The renderer accepts posts only from the blog’s HTTPS domain, escapes feed text, rejects external XML entities, sorts by publication time, and handles dates consistently across PowerShell versions. Saved featured-post details keep the chosen article available when it leaves the RSS window.
